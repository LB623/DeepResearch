60 秒开场 · 建议口述

我独立开发了 DeepResearch，一个基于 LangGraph 的多阶段研究 Agent。它先拆解问题并让用户确认计划，再并行检索、评估证据缺口，最后通过 Writer / Critic 循环生成带引用的报告。我的主要工作是把长任务的状态、事实记忆和评测闭环做扎实：用 Checkpoint 支持恢复，用 Milvus 管理事实及其时效性，并通过受控检索 A/B 和固定题集评测定位问题。最有代表性的优化是查询状态去重和质量感知重排；相关指标都有明确的测试集口径。

为什么需要它

一次检索回答难以覆盖复杂主题；多轮研究会产生重复状态、过期事实、证据缺口和引用丢失。项目把这些问题显式建模为图状态和路由。

Agentic RAG 的具体含义

LLM 参与制定计划、生成查询、判断证据充分性和决定后续搜索；Milvus 的历史事实给查询生成提供上下文，新事实再写回。不是上传文档后固定检索一次。

个人职责与范围

简历口径：个人项目、独立开发，覆盖主图与子图、事实库、状态恢复、质量护栏和评测。不要额外声称线上用户量、生产 SLA 或商业落地。

时间线先对齐 简历写 2026.03–2026.07，但所引检索 v2 报告记录于 2026.08.16。若 8 月继续迭代，可据实调整结束时间或单列“8 月补充评测”；不要把 8 月实验说成 7 月已完成。本页按当前本地工作区与历史记录整理，包含尚未提交的检索扩展，不等同于 7 月快照。

研究循环

预算检查↓召回已有事实 → 生成查询↓ 规范化去重 + 剩余额度截断Send 并行搜索 → 摘要 + 来源 + 事实落库↓ 汇合Critique：is_sufficient / knowledge_gap↺ 缺口查询再次检索；满足条件则退出

停止条件包括：证据足够、最大循环数、搜索预算、无进展、全局 token / 时间预算，或没有可执行的新查询。模型认为“足够”是启发式判断。

写作循环

预算检查 → Outline↓Draft：材料 + 大纲 + 上一版草稿↓Critic：缺陷、严重级别、是否可润色↺ 未就绪且未达修订上限 → DraftCite & Polish → 确定性校验 → Finalize全局预算耗尽 → 已有草稿 / 证据兜底

研究 Critic 判断“材料够不够”；写作 Critic 判断“报告好不好”。修订数达到上限也会进入润色，不能保证所有问题都解决。

核心难点 · Reducer 与边界

为什么会从 N 变成 2N？

先区分“业务动作执行了一次”与“结果在状态中记了两次”。

原始问题

生成与执行共写累加字段

generate: [q1,q2,q3]＋ operator.addsearch: [q1,q2,q3]search_query = 6 条

网页搜索本身仍执行 3 次；状态中出现 50% 重复，导致后续统计、成本归因和引用追踪失真。

修复之后

分离语义 + fan-out 前去重

generated_queries = 3 条executed_queries = 3 条skipped_duplicate_queries状态查询数 = 3 条

执行节点不再把查询追加回 search_query。规范化去重也覆盖 follow-up，已执行集合参与过滤。

状态类型代表字段更新规则 / 面试关注点
消息messages / plan_messagesadd_messages；不是简单重复拼接全部历史。
累加列表generated_queries / executed_queries / sources_gathered / web_search_resultoperator.add；每个节点返回增量，不要把累计状态再次回传。

核心难点 · 事实检索

先扩大候选，再竞争最终的 K 个位置

原始相似度 Top-K 可能被重复、过期和低质量记录占位；扩大候选让过滤和去重后还有补位空间。

01Query embedding一次向量化，A/B 复用
02Milvus 召回 3K默认倍率 3，可配置
03过滤与衰减置信度门槛 + 年龄 / 类别 TTL
04质量重排相关性 + 置信度 + 新鲜度
05规范化去重按最高分保留一个规范化文本
06返回 Top-K不保证每次都能补满
retrieval_score0.65 × relevance + 0.25 × confidence + 0.10 × freshnessrelevance 为 COSINE 相似度，越大越好；confidence 在启用 decay 时使用衰减后的值。是确定性加权规则，不是 LLM reranker。
操作演示 · 人工示意数据

切换策略，观察候选怎样占位

固定 K=5，模拟原始相似度排序。仅帮助理解机制，不复现真实 Milvus 实验或评测指标。

为什么是 3 倍？

工程上用适度额外召回来缓解过滤后的候选不足。现有记录支持“默认选择 3”，不支持“3 是全局最优”。要证明倍率选择，应比较 1 / 2 / 3 / 5 倍的质量、延迟和候选量。

去重到底是什么？

代码用 Unicode 正则去掉非 word 字符，再转小写；属于规范化文本去重。不能合并所有语义相同的改写，也不能自动消解事实冲突；0% 仅是受控集及该指标口径。

置信度可以信吗？

confidence 是存储的事实质量信号，不是经校准的真值概率；与新鲜度一起参与启发式排序。权重与打分尺度会影响结果，不能把高分直接解释成事实正确。

Milvus 记事实，Redis 分别记缓存与任务

三个存储用途不同，因此它们的失败策略也不同。

Fact 记录

机制实现要记住的边界
freshness（默认）high 7 天 / medium 30 天 / low 180 天来自计划阶段的 fresh_level；显式“开始研究 / 需求确认”快捷路径设为 medium。
lifecycle（可选）market_data 7 天；product_info 30 天；strategy 90 天；technology 180 天；historical 无 TTL按类别过滤；历史事实不设 TTL 不等于内容永远正确。
confidence decayraw_confidence × max(0.3, 1 − age / (2 × horizon))低置信度门槛检查发生在衰减前；衰减后的 confidence 影响重排。
off / informoff 不过滤、不衰减、不标年龄；inform 只加年龄标记和提示告知模型旧事实可能过期，避免“已有事实就禁止再次搜索”。
时间与冲突的真实边界 created_at 缺省是入库时间，可能不同于事实发生时间或来源发布时间。因此“新入库”不一定“内容新”。当前规范化去重也不构成版本替换或冲突裁决系统。
存储保存什么失败时为什么
Milvus FactStore跨任务语义事实记忆不中断研究；初始化失败冷却后重试，默认 30 秒事实库是增强能力，在线检索仍可继续。
Redis Search Cache以 prompt、count 生成 key；结果默认缓存 3600 秒降级进程内缓存只影响性能和跨进程复用。
Redis Checkpoint图状态与待执行位置配置 redis 时默认 fail closed静默退内存会破坏“重启可恢复”承诺；本地可显式打开 fallback。

可靠性 · 不从零开始

恢复计算进度，也恢复预算

恢复不是把任务再提交一遍；需要稳定任务身份、持久状态和明确重试边界。

故障注入
生成 3 个查询 ✓搜索 3 次 ✓Critique ×报告

Restart

从头重跑 → 再生成、再搜索

6 次搜索

查询生成 2 次 · Critique 2 次

Resume

相同 thread_id → 读取 pending critique

3 次搜索

查询生成 1 次 · Critique 2 次

实验与能力分开说 上面的 6→3 来自 memory checkpoint 的确定性故障注入 harness，证明该失败位置可以复用已完成节点，不是 Redis 跨进程恢复的实测 SLA。代码另有 Redis 持久化路径；LangGraph API runtime 下会禁用这里的自建 checkpointer，交由运行时管理。

恢复入口

同一 thread_id 调用 ainvoke(None, config)，恢复待执行节点；传入新消息则在 checkpoint 状态上启动新图步骤。需要检查 snapshot.next，而不是只判断是否有历史消息。

不能承诺 exactly-once

若外部搜索已经成功，但写 checkpoint 前失败，节点可能重放。Checkpoint 避免的是已稳定落盘工作重复执行；外部副作用仍需要幂等键、结果缓存等保护。

SSE 与任务恢复不同

前端使用 LangGraph SDK、streamResumable 等配置接收长任务事件。流断线续传解决事件接收；checkpoint resume 解决图执行进度，两层不要混为一谈。

预算是一组持久状态，不是进程局部变量

01进入节点前检查墙钟时间、已用 token
02并发派发前按剩余搜索次数裁剪查询
03调用完成后把新增用量累加到 state
04证据反思后比对 evidence fingerprint
05达到停止条件结束研究 / Writer 使用兜底

run_started_at、web_search_call_count、llm_token_count、no_progress_rounds、budget_stop_reason 随图状态持久化。token 通常在调用完成后计入，边界检查并不等于对在途调用的硬实时中断。无进展检测比较证据载荷指纹，不是语义等价判断。

Draft 的护栏

对照大纲检查章节；缺失时定向补全。修订输入显式包含上一版草稿，避免 Critic 提了意见但 Writer 从零再写。

Polish 的护栏

启用质量护栏时检查长度比例、章节保留、URL 白名单和部分专名；不合格时回退完整 draft。长度比例阈值在当前实现中为 0.75。

Critic 的分工

研究 Critic 输出证据缺口；写作 Critic 输出修改意见和就绪状态，使用 reflection_model。最终一次反馈也会传入 polish。

不能保证“零幻觉”

确定性检查是局部约束；专名规则是启发式，URL 白名单也不能证明引用支持具体论断。需要 claim–evidence 对齐、来源分级与人工抽检。

最好的面试解释 “我从纯提示词约束走到提示词 + 程序校验 + 回退，并用固定集检查收益。历史 5 题 v3 中 Judge 未判定幻觉，但覆盖和时效性下降，所以我没有把它说成全面质量提升。”

NDCG 怎样算？

DCG@K = Σ (2^gain − 1) / log₂(rank + 1)

NDCG@K = DCG@K / IDCG@K

rank 从 1 开始；相关性有等级，排得越靠前贡献越大。与仅判断“有没有相关结果”的指标相比，它更关注排序质量。当前评测对规范化文本重复的事实 只给首次命中增益。

配对 bootstrap：以查询为单位对 baseline / optimized 成对有放回采样，计算均值差，重复 10,000 次，取 2.5% / 97.5% 分位数。固定测试集上的区间不跨 0，不等于真实线上必然提升。

K=10 的反例必须会讲

Unique Precision@10：37.7% → 34.1%
Recall@10：75.4% → 68.3%
NDCG@10：41.5% → 46.0%

NDCG 差值 CI 为 [−0.9, +9.8] pp，跨 0。不能说所有 K 都提升。结果提示权重与候选选择有取舍；可能的原因需要分桶与消融验证。

有效槽位率 82.6%→100% 与 Recall 回退可同时发生：位置补满了，不代表补进来的都是更相关事实。

Judge 五维对照：只说实际改善的维度

综合均分：4.36 → 4.24（−0.12）；Judge 幻觉判定题数：3/5 → 0/5。事实准确性 3.6→4.0、逻辑结构 4.6→4.8 是真实记录，但不能省略覆盖与时效回退后宣称“整体报告质量提升”。

确定性加权重排透明、可复现、不增加 LLM rerank 调用权重未必最优、语义重复与冲突未解；下一步做消融、分域分析、语义去重对照。
并行 fan-out独立查询可并发执行，缩短等待链聚合、限流、任务额度分配更复杂；并发量与供应商限额需要联合控制。
Writer–Critic 有限循环将修改意见纳入生成，避免无限修订额外 token / 延迟；Critic 有偏差，达到次数上限也可能仍有缺陷。
LLM-as-Judge可扩展地评价报告的多个维度非真值，受提示词与模型偏差影响；下一步固定版本、重复运行、盲评顺序、人类校准。
Checkpoint 持久状态复用已完成计算，支持失败恢复不能自动保证外部副作用 exactly-once；需要幂等、运行身份与恢复集成测试。

全部追问与参考答案

01用一分钟介绍项目。项目表达

背景 → 流程 → 个人难点 → 证据 → 边界。长链路研究状态易乱、事实会旧、引用会丢；主图确认计划，Research 迭代检索，Writer 审稿生成；挑查询状态或重排讲深。不要开场罗列所有技术栈。

02为什么不用一个大 Prompt 一次写完？架构

复杂主题需要外部证据、用户确认和多轮补缺。拆图让每阶段输入、状态、停止条件和失败位置可观察；代价是编排、状态聚合及模型调用成本增加。

03两个 Critic 有什么不同？架构

Research Critic 看证据充分性与缺口，输出后续查询；Writer Critic 看草稿问题并控制修订 / 润色。一个评价材料，一个评价表达和论证。

04为什么 N 条查询会记录成 2N？状态

累加 reducer 上，生成节点与执行节点各返回同一查询。实际执行 N 次，状态 2N。分离 generated / executed / skipped，执行结果不回写 search_query，并在派发前去重。

05父子图为什么也会重复累加？状态

子图返回累计状态，父图 reducer 再次追加历史。通过 _subgraph_delta_updates 返回列表后缀和计数差，保持增量契约；Writer 不把去重来源列表再次追加回父图。

063 倍过采样解决什么？检索

Top-K 先被过期与重复项占位，过滤后不足。先召回 3K 扩大补位空间，再过滤、重排、去重取 K。不是调用 3 次 embedding，也不保证始终 K 条。

07重排公式和去重规则是什么？检索

0.65×相关性 + 0.25×置信度 + 0.10×新鲜度。启用 decay 时 confidence 已衰减。规范化删除非 word 字符并转小写，按分数保留首次；不是语义聚类。

080% 重复率是不是彻底解决重复事实？检索

不是。只是在受控测试集与规范化文本去重指标口径下为 0；语义改写可能保留，矛盾事实不会被自动裁决。应分开设计语义去重与版本 / 冲突处理。

09为什么用 NDCG@5？评测

它评价带等级相关性的前排排序。DCG 使用增益与位置折扣，除理想排序 IDCG 得到归一化值；当前评测对规范化文本重复的事实 后续命中不给增益。

1095% CI +9.3～+20.3 怎样得到？评测

70 个 test 查询逐题配对，bootstrap 成对有放回采样，算均值差；10,000 次后取 2.5% 和 97.5% 分位。单位是百分点，不是相对百分比。区间仅反映固定集配对差异的抽样不确定性。

11这些检索指标能证明报告质量提升吗？评测

不能。真实 Milvus + bge-m3，但语料是受控合成集；它验证组件排序、过滤和去重。报告质量要单独跑端到端固定集及重复评测。

12优化有什么反例？评测

K=10 Precision / Recall 回退，NDCG 增量 CI 跨 0。E2E v3 事实与结构改善，但总均分 4.36→4.24，覆盖和时效下降。这些结果需要保留，下一步做消融和重复运行。

13为什么 Redis 有两种降级策略？可靠性

Search Cache 是优化，失败退内存还能完成研究；Checkpoint 承担持久恢复承诺，redis 配置下连接失败默认关闭任务路径，避免静默失去持久性。

14Resume 是否保证外部调用只执行一次？可靠性

不保证。稳定 checkpoint 后可跳过已完成节点；调用成功但 checkpoint 前故障可能重放。幂等键、结果缓存和外部副作用设计仍然必要。

15故障实验的 6→3 与查询 2N→N 是一回事吗？可靠性

不是。前者是 memory checkpoint 故障注入下，恢复比从头重跑少 3 次搜索；后者是查询状态记录修复，实际搜索都是 N 次。不能混用成本结论。

16任务恢复以后预算会重置吗？可靠性

不应重置。开始时间、搜索调用数、token、无进展轮数等保存在 LangGraph state。各节点返回增量，父子图也要避免重复累计。当前检查在节点边界，不等于硬实时中止调用。

17Milvus 挂了怎么办？可靠性

事实记忆作为可选增强，读写失败不阻断研究。FactStoreProvider 初始化失败后冷却重试，默认 30 秒，锁避免并发重复初始化；不是永久 disable。

18如何判断事实过时？记忆

默认 freshness 按 high/medium/low 使用 7/30/180 天；可选 lifecycle 按类别 TTL。created_at 默认为入库时间，不能冒充事件时间，应补来源发布时间和事实有效期。

19报告 URL 都合法就可信了吗？引用

不等价。还需知道来源是否权威、内容是否支持论断。现有归一化和白名单避免引用链丢失或新增 URL；不保证语义蕴含，下一步做 claim–evidence 验证。

20为什么 polish 失败要退回 draft？引用

模型润色可能截断、漏章节、新增专名或来源。程序检查不通过时保留完整草稿，避免较晚的一次生成破坏已有质量；兜底仍不保证 draft 没有事实问题。

21你会怎样设计下一轮可信 A/B？评测

固定模型、题集、参数与来源快照（可行时）；分离唯一变量；按题配对、多次重复；报告均值、方差、胜率、失败样本和维度回退，并做人类抽检。

22最值得先做的改进？改进

先保证评测可解释：核心固定集重复 A/B 与人类校准；检索做倍率 / 权重 / 去重消融。再补事件时间、版本冲突和证据级校验，而不是仅堆更多 Agent。

23为何简历截至 7 月却引用 8 月实验？项目表达

先核对真实经历。若 8 月仍在迭代，应更新截止时间，或明确 3–7 月开发、8 月补充评测。保留真实日期，避免对历史成果的错误归属。

24人工确认一定使用 interrupt 吗？架构

当前主图是 plan_status 和 awaiting_plan_confirmation，再次提交后进行确认 / 重规划；并未直接调用 interrupt()。恢复待执行节点与提交新的人类反馈是不同输入路径。
